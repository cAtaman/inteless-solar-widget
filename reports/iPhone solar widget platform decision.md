**iPhone solar widget platform decision — 21 October 2026**

**Scriptable is the best first candidate for your widget, conditional on a successful background-authentication test.** Pyto remains a credible choice if using Python matters enough to justify extra secure-storage and runtime integration. SwiftUI/WidgetKit is the stronger route for a standalone app and explicit platform control, with more installation and maintenance work. None requires an always-on server by design. Neither hosted option has been validated against your account or inside your iPhone’s widget process. My earlier recommendation was too confident about that distinction.

Code changes are paused. The workspace contains unfinished JavaScript core/authentication helpers and a build script; there is no completed widget UI, generated installable script, or test suite yet. During this comparison, only research notes and this report were added. No credentials, authenticated telemetry, or account login requests were used.

| Decision point | Scriptable | Pyto | Native SwiftUI/WidgetKit |
|---|---|---|---|
| Language and delivery | JavaScript inside Scriptable | Python inside Pyto | A signed iPhone app and widget extension |
| Actual Home Screen widget | Supported | Supported | Supported |
| Server requirement | None if direct cloud authentication works | Same | Same |
| Secure local password entry | Documented masked field | Documented secure text field | Native secure field |
| Credential storage | Documented encrypted Keychain wrapper | Apple Security bridge appears feasible; no ready-made shared wrapper verified | Explicit Keychain and access-group control |
| Cloud login crypto | Additional JavaScript crypto and secure randomness needed | Convenient Python options, but widget-package support is uncertain | Documented native RSA support |
| Automatic freshness change | Dynamic age; no documented public multi-snapshot timeline API | Documented future timeline entries | Native future timeline entries |
| Installation burden | Install host, import script, configure widget | Install/unlock host, import script, configure widget | Build/sign/install and maintain distribution |
| Main unresolved gate | Secure full re-login inside the background widget | Shared Keychain, verified TLS, crypto and autonomous execution | Signing, entitlements and account integration |

The platform claims in this table come from the [Scriptable APIs](https://docs.scriptable.app/), [Pyto widget guide](https://pyto.readthedocs.io/en/latest/library/widgets.html), and [Apple’s widget-extension documentation](https://developer.apple.com/documentation/widgetkit/creating-a-widget-extension). “Documented” does not mean tested on your phone.

The monitoring service imposes the same requirements on both languages. The live Inteless site identifies itself as `powerview`; its shipped code includes AlpSolarr-specific device handling and separate PV Pro layouts. That supports a shared platform relationship, **not interchangeable branded accounts, servers or APIs**. We should start with your supplied host and only change region if your account requires it. ([Live Inteless site](https://pv.inteless.com/), [shipped application](https://pv.inteless.com/static/js/app.c55d2bbc.js))

The current login fetches an anonymous public key, signs that query with MD5, encrypts the password using randomized RSA PKCS#1 v1.5, and posts to `/oauth/token/new`, with `client_id=csp-web` and a default source of `elinter`. The anonymous key request succeeded; its returned RSA key was 4096 bits. This establishes the public-key service, not account login. The older plain-password examples are insufficient evidence for today’s flow. ([Current application code](https://pv.inteless.com/static/js/app.c55d2bbc.js))

The login UI also handles email verification and required password changes. Either widget must stop automatic retries and show “sign in required” when human interaction is necessary. Actual token lifetime, refresh rotation and recovery remain unknown; the web client’s refresh wrapper is unusual enough to require an account-backed check. Choosing Python does not remove these service requirements. ([Current login module](https://pv.inteless.com/static/js/7362.49d65aba.js))

Scriptable’s advantage is its focused iOS API. It documents HTTP headers, JSON, timeouts, status codes and redirect control; insecure requests are rejected by default. It also documents encrypted Keychain storage and local persistence. That gives us a straightforward foundation for token handling and cached telemetry. App-to-widget storage access, locked-phone behavior and behavior after reboot still need testing. ([Request](https://docs.scriptable.app/request/), [Keychain](https://docs.scriptable.app/keychain/), [FileManager](https://docs.scriptable.app/filemanager/))

Its crypto gap is real but **not yet a proven blocker**. Scriptable uses JavaScriptCore, so browser `crypto` and Node’s `crypto` cannot simply be assumed available. No native RSA or cryptographic-random API was found in its public API. A local WebView can evaluate JavaScript, and WebKit provides secure randomness, but the documentation does not establish that this works reliably inside a current Scriptable Home Screen widget. A vetted crypto implementation must prove its random source there; `Math.random` is unacceptable. Foreground login alone would not settle unattended recovery after refresh-token rejection. ([Scriptable environment](https://docs.scriptable.app/), [WebView](https://docs.scriptable.app/webview/), [WebKit cryptography](https://webkit.org/blog/7790/update-on-web-cryptography/))

Pyto offers Python’s familiar HTTP, hashing and secure-random tools, plus a documented widget timeline API. However, its older documentation warns that autonomous widgets cannot import most native-extension libraries. Inspected source includes machinery to load some native frameworks, so **“cryptography cannot work” would overstate the evidence**. The exact installed build must decide this. A vetted pure-Python RSA implementation or Apple Security bridge is an alternative, with additional work. App-assisted execution exists, but its documented workaround recommends recurring Shortcuts automation; that is extra upkeep. ([Pyto widget modes](https://pyto.readthedocs.io/en/latest/library/widgets.html), [framework importer](https://github.com/ColdGrub1384/Pyto/blob/510cd710846e702437618d472dee439f855cb576/Lib/extensionsimporter.py#L625), [Python secure randomness](https://docs.python.org/3.10/library/secrets.html))

Pyto’s commonly documented `userkeys` is JSON-backed storage, **not a substitute for Keychain**. Its app and widget declare the same app group, and Apple allows app-group identifiers to serve as Keychain access groups. A shared Apple Security bridge therefore looks feasible, but has not been implemented or tested. Secure text entry is supported; secure persistence needs separate verification. ([userkeys](https://pyto.readthedocs.io/en/latest/library/userkeys.html), [Pyto UI source](https://github.com/ColdGrub1384/Pyto/blob/510cd710846e702437618d472dee439f855cb576/Lib/pyto_ui.py#L6075), [Apple sharing rules](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps))

A security-relevant source finding deserves qualification: the inspected Pyto widget bootstrap changes Python’s default HTTPS context to an unverified context. This affects callers using that default; it does **not** prove every Pyto connection skips certificate verification, or that the installed binary matches that revision. Requests with verification enabled or an explicit verified SSL context can avoid that default. Before real credentials are entered, a Pyto implementation must demonstrate rejection of an invalid certificate in its widget process. ([Pinned bootstrap](https://github.com/ColdGrub1384/Pyto/blob/510cd710846e702437618d472dee439f855cb576/Widget/SetupPython.swift#L35), [Requests TLS verification](https://requests.readthedocs.io/en/latest/user/advanced/#ssl-cert-verification))

Freshness is a material difference. iOS controls reload opportunities; neither platform gives continuous telemetry. Apple describes roughly 40–70 daily reloads for frequently viewed widgets, often 15–60 minutes apart, with substantial variation. Scriptable’s `refreshAfterDate` is earliest eligibility, not a deadline. Its dynamic date text can keep showing increasing age, but a static green “fresh” badge could outlive its validity. Pyto and native timelines can schedule an already-cached snapshot labeled stale later, without another network request. That improves presentation control, not cloud-data freshness or scheduling guarantees. ([Apple refresh guidance](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date), [Scriptable refresh](https://docs.scriptable.app/listwidget/), [dynamic dates](https://docs.scriptable.app/widgetdate/))

All requested readings can fit conceptually in either host, preferably a large widget, but actual field availability remains account-dependent. The current client exposes plant/inverter enumeration and separate flow, battery, PV and grid telemetry routes. Its display distinguishes household/EPS loads and uses explicit flow flags rather than one universal power-sign convention. Source timestamps, string voltages, grid availability, units and direction still require comparison with AlpSolarr. No inverter model is needed to begin login and enumeration. Missing values must remain unavailable, and cached values must retain their original source age. ([Current telemetry client](https://pv.inteless.com/static/js/app.c55d2bbc.js), [flow display](https://pv.inteless.com/static/js/3898.7188df33.js))

A native app provides documented RSA, explicit Keychain policy and timeline control. It normally requires compatible Mac/Xcode tooling and Apple signing. Free Personal Team provisioning expires after seven days; paid Developer Program membership is US$99 annually, with regional pricing possible. Exact entitlements and distribution still need checking. Native is worthwhile for a standalone product, but it does not remove interactive cloud login or iOS refresh limits. ([Native RSA](https://developer.apple.com/documentation/security/seckeyalgorithm/rsaencryptionpkcs1), [Xcode requirements](https://developer.apple.com/xcode/system-requirements), [Personal Team limits](https://developer.apple.com/help/account/basics/about-your-developer-account), [membership](https://developer.apple.com/help/account/membership/program-enrollment))

When you resume, the decisive checks are local: verified HTTPS; masked credential setup and shared Keychain/cache access; foreground and actual-widget authentication; expired/rejected token recovery; offline/rate-limit fallback; source-age behavior across delayed refresh, locking and reboot; and readings compared with AlpSolarr. Those checks should precede choosing Pyto purchases or treating Scriptable as an unattended solution. **For now, the evidence supports trying Scriptable first, choosing Pyto for a meaningful Python preference, and choosing native for standalone-app control. Implementation remains paused.**
